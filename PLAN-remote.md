# orc — remote backends, instances and multi-window

Status: revision 13 — final; the last Fable review (of revision 12) returned "plan is ready" with five text-level items, folded in here. Revision 5 was reviewed "ready" by Fable; revisions 6–8 added the zero-prerequisite host setup (self-contained server bundle, token forwarding — §8, §11, phases 3b/3c), reviewed twice more with "plan is ready" on the last pass. Revisions 9–10, by the owner's decision: one delivery path (the host downloads the bundle), no npm route, and the server runs on **Node** (a Single Executable Application built from the exact Node version Electron ships) rather than Bun, so the engine runs on one runtime everywhere. Revision 11 folds in Fable's review of that change, which included building a working SEA from the SDK wrapper. Scope: running the UI on one machine and the engine on another (VS Code Remote-SSH style), instance exclusivity, multiple windows.

## 1. Vocabulary

| Term | Meaning |
|---|---|
| **Engine** | The backend: `engine.ts`, codecs, stores, the SDK/`claude` processes. Owns chats, transcripts, asks, statuses. Today it runs inside Electron's main process. |
| **Client** | The React UI (the renderer). Talks only through `OrcApi` (`src/shared/api.ts`: 17 request/response methods — 4 `projects`, 9 `sessions`, `answerAsk`, `codecInfo`, 2 `settings` — plus 5 push events). |
| **Transport** | How a client reaches an engine: Electron IPC in-process (today), or NDJSON over an ssh child process's stdio (new). |
| **Target** | A data dir + the `~/.claude` next to it, on some machine, for one Unix user. "Local" is a target; "devbox" is a target. Opening a machine locally and connecting to it remotely (as the same user) are the *same* target and show the same projects, chats and settings — see §8 for the data-dir default that guarantees it. |
| **Instance** | One engine + exactly one client. A local instance is one Electron app with the engine in-process. A remote instance is an Electron window on machine A driving an `orc-server` on machine B. |

## 2. Invariants

1. **One engine per target** at any time — a lock file in the data dir plus a take-over handshake (§6).
2. **One client per engine.** With stdio as the only transport every connection *is* its own server process, so this follows from invariant 1: a second connection is a second server, which finds the lock held. (Taking over therefore always restarts the engine; there is no "adopt a running engine" path.)
3. **One instance per target per launching machine.** The local target keeps today's `userData`; a remote target gets `<userData>/remote-<host>`. `app.requestSingleInstanceLock()` is keyed on `userData`, so a second launch of the same target focuses the existing window, and different targets run side by side. On macOS each instance is a separate process with its own Dock icon and menu bar — accepted.
4. The renderer does not know which transport it is on beyond a `transport:state` push (host chip, connecting/busy screens, clock offset).

Today none of these hold: launching the app twice gives two engines on the same `sessions.json`.

## 3. Current coupling (what has to move)

Electron is imported in exactly four main-process files:

| File | Electron use | Replacement |
|---|---|---|
| `src/main/ipc.ts` | `ipcMain.handle` binding, `BrowserWindow` fan-out in `push()`, `dialog.showOpenDialog` in `projects.add` | handlers become a plain object (`src/server/handlers.ts`); `push` is a sink the transport provides; the folder dialog moves to the desktop IPC layer (§7.3) |

Everything else in `src/main` (engine, reducer, codecs, fake SDK) is plain Node already. The renderer has no Electron dependency.

The server is delivered to hosts **only** as the Node SEA bundle (§8); nothing is published to npm and `package.json` keeps its name. `handlers.ts` implements `Omit<OrcApi, 'on' | 'transport'>` with `projects.add` taking a required path; the desktop IPC layer serves `transport.*` and the path-less `projects.add` itself and never forwards them.

## 5. Wire protocol (stdio transport)

NDJSON over the server process's stdin/stdout (stderr is logging), one frame per line — the framing the SDK itself uses with `claude`.

```
client → server   {"hello": {"version": "0.2.0", "client": {"host": "laptop", "user": "yuval"}, "takeover": false, "oauthToken": "sk-ant-oat01-…"}}   // oauthToken optional, §8
server → client   {"ready": {"version": "0.2.0", "host": "devbox", "dataDir": "...", "now": 1792440000000}}
                | {"busy": {"holder": {"host", "user", "client": {"host", "user"}, "since", "kind": "local"|"server"}}}   // lock held; server stays up waiting for a second hello
                | {"error": "not-logged-in", "claude": "/path/to/claude"}                                            // §8; server exits after sending it
client → server   {"hello": {..., "takeover": true}}                                      // after busy: take the lock (§6), then ready
client → server   {"id": 7, "method": "sessions.send", "args": ["<sid>", "hello"]}
server → client   {"id": 7, "result": null} | {"id": 7, "error": "Session not found: ..."}
server → client   {"event": "transcript:patch", "payload": {...}}                        // the existing PushEvents
either direction  {"ping": 1} / {"pong": 1}                                             // client every 15 s
client → server   {"shutdown": true}                                                    // graceful: closeAll(), release lock, exit
```

- `method` is the dotted path the preload uses today (`projects.list`, `sessions.send`, `asks.answer`, `codec.info`, `settings.get`…), so `handlers.ts` is the single implementation for both transports. New methods: `projects.browse`, `sessions.markRead` (§7.1); `projects.add` gains an optional `path`.
- Errors carry the same text the IPC path throws today; the renderer already shows them as error notes. The stdio client queues requests until `ready` and rejects everything pending with "Disconnected" when the server exits.
- **Pre-frame noise**: the host's shell profile may print to stdout before `exec` hands over (banners, oh-my-zsh, p10k). The server writes nothing before its first frame; the client discards and logs any line that is not JSON until `ready`/`busy`/`error` (not merely the first `install` frame — the install steps run in between), and shows those (host-stdout) lines on the error screen if the handshake fails. The bootstrap keeps its own stdout clean the same way: it saves the real stdout as fd 3 (`exec 3>&1 1>&2`), writes frames to `>&3`, and hands fd 3 back on the final `exec orc-server --stdio 1>&3 3>&-`, so tool chatter such as `sha256sum`'s `bundle.tgz: OK` goes to stderr. The client reads the ssh child until `close` (not `exit`) so a `taken-over` frame written just before exit is still parsed.
- **Install frames** (phase 3c, emitted by the bootstrap script before the server starts): `{"install": {"phase": "downloading"|"verifying"|"unpacking"}}` drive the installing screen (no byte counts: `curl -fsSL` is silent, and the one-time size is already in the screen text); `{"error": "install-failed", "reason": "no-curl"|"download"|"sha256"|"unsupported-host"}` ends the attempt.
- After `busy`, the client re-sends the **full** `hello` with `takeover: true` (token included); the server uses the last `hello` it received. The desktop's own frame log redacts `hello.oauthToken`.
- `ready.now` → the desktop computes `clockOffset` and includes it in `transport:state`; the renderer's `useNow()` adds it. `task.startedAt/endedAt` are server `Date.now()` values and the panel compares them with the client clock.
- Version mismatch cannot happen by construction: the launcher always runs `~/.orc/<app version>/orc-server`, and from phase 3c installs it when absent (in phase 2 the dev script of §7.4 pushes it). The handshake still compares `ready.version` with the app's full version and shows "Server is 0.1.9, this app is 0.2.0" as a guard against a hand-copied bundle.
- Pings start right after `hello` (not at `ready`), so a server sitting on the busy screen is kept alive while the user decides. Server liveness: the timer starts at the first client frame; no frame for 45 s → the server treats the link as dead: `closeAll()`, release the lock, exit. This covers half-open TCP (laptop sleep, Wi-Fi change) where sshd never notices; without it a stale server would hold the lock and every reconnect would hit the take-over dialog.
- Client-side dead-link detection is delegated to ssh: the launcher passes `-o ServerAliveInterval=15 -o ServerAliveCountMax=3`, so ssh exits after 45 s of silence (matching the server's timer) and the existing exited → disconnected → backoff path runs. The client ping exists only to feed the server's timer; no pong bookkeeping or per-request timeouts.
- Server exit paths, all running `closeAll()` first so no `claude` child is orphaned: stdin `end`, `SIGTERM`, `SIGHUP`, stdout `error` (EPIPE), and the ping timeout.

The desktop ↔ renderer side: `transport.state()` (request, called in `init()` so a state pushed before the page loaded is not lost) and the push event `transport:state` for deltas, both carrying `{ kind: 'local' | 'remote', host?, phase: 'connecting' | 'starting' | 'busy' | 'ready' | 'disconnected' | 'error' | 'taken-over', holder?, error?, clockOffset }`. It drives the connecting screen, the host chip and the banners (§7.2). `transport.takeover()` and `transport.reconnect()` are `OrcApi` methods too; all three land in phase 0 together with the busy screen.

## 6. Lock and take-over

`<dataDir>/lock` (JSON), written with `wx`: `{ pid, startedAt, host, user, client: { host, user }, since, kind: 'local' | 'server' }`. `host`/`user` identify the holder *process* (used for liveness); `client` identifies who is driving it — `hello.client` for a server, the same as `host`/`user` for a local holder — and is what the busy screen shows and the auto take-over compares. `startedAt` is the holder process's start time: `ps -o lstart= -p <pid>` run with `LC_ALL=C` (the output is locale-dependent — a Finder-launched holder and an sshd-launched taker can have different `LANG`, and a mismatch would make every lock look stale) on macOS, `/proc/<pid>/stat` start time on Linux — split the text after the last `)` (the comm field may contain spaces) and take index 19, since `pid` and `comm` are already consumed; the trimmed string is compared verbatim.

- **Liveness**: `host === os.hostname()` and `kill(pid, 0)` succeeds (an `EPERM` counts as alive) *and* the process start time matches `startedAt`. A mismatch means the pid was recycled → stale → replaced silently. A different `host` (shared home on NFS) counts as live with no take-over offered ("controlled from another machine").
- **Held** → the new engine does not start. The renderer shows the busy screen: *"orc is already running for this folder, controlled by yuval@laptop since 10:42"* (`holder.client`) with **Take over** / **Cancel** (both local and remote use the same screen, via `transport:state`; no native dialog, so Playwright can drive it).
- **Take over**: the taker first writes `<dataDir>/takeover` (`{ client: { host, user }, at: Date.now() }`), then SIGTERMs the holder (same host by the rule above). A SIGTERM carries no payload, so this file is how the holder tells a take-over from a plain `kill`/logout and learns who took over. The holder's handler runs `closeAll()` — which interrupts running turns, denies pending asks with "Session closed" and settles tasks, exactly like closing the window today — releases the lock, and reads-and-unlinks `takeover`, ignoring one older than 30 s (a taker that died between writing it and taking the lock must not turn a later logout into a "take-over"). If it was a fresh take-over: a local instance with a window stays up in phase `taken-over` showing *"Taken over by alice@devbox"* with **Take back** (with no window open — macOS keeps a local instance in the Dock — it simply quits), a server writes `{"event": "taken-over", "payload": {"by": …}}` to its client and exits; otherwise it is an ordinary quit, as today. The taker removes `takeover` after writing its own lock if it is still there. The taker polls for the lock to disappear for 5 s; if it is still there the holder's event loop is stuck, so the taker SIGTERMs the holder's children first (`pgrep -P <pid>` — the `claude` processes, which only the SDK's `close()` would otherwise stop), then SIGKILLs the holder and replaces the lock. The `wx` write can still lose to a concurrent taker → EEXIST loops back to the handshake, never crashes.
- **Auto take-over**: the desktop sends `takeover: true` without asking when `busy.holder` is `kind: 'server'` and `holder.client` equals our own host+user — that is our previous server from a dropped link, not another person.

## 7. Desktop shell changes

### 7.1 Instances and windows (phase 3a)
- `orc` → local target; `orc --remote <host>` → remote target (`userData` per §2.3). The shell's `userData` and the engine's data dir are separately overridable: `ORC_USER_DATA_DIR` (shell; defaults to `ORC_DATA_DIR` when that is set, else today's path) is applied with `app.setPath('userData', …)` *before* `requestSingleInstanceLock()`. Tests and a dev instance therefore never collide, and `lock.spec` can run two instances with distinct `userData` on one shared `ORC_DATA_DIR`.
- **File → New Window** opens another window on the same instance. `menu:new-chat` goes to the focused window only. Bounds are stored per window index in the shell-local file.
- `unread` moves onto `Session` (`sessions.update`, pushed with `sessions:changed`, so it survives the idle close and a reconnect's refetch — statuses of closed chats are dropped on load): the engine sets it on running→idle, and on running→closed except during its own shutdown (`before-quit`/`shutdown` → `closeAll()` must not leave a dot on every chat that happened to be running); `sessions.markRead(id)` clears it. The renderer whose `activeId` is that chat calls `markRead` as soon as the flag arrives, so a chat you watched finish never shows a dot elsewhere; `select()` calls it too (today it skips `open()` for cached chats). This keeps today's behaviour exactly, across windows.

### 7.2 Connecting to a host (phase 2)
- ⌘K → **Connect to host…**, and a **Remote…** row in the project chooser strip. Lists `Host` entries from `~/.ssh/config` (wildcards skipped), recent hosts from the shell-local file, and **Add host** (`user@host[:port]`).
- Picking a host launches `orc --remote <host>` as a new detached process (§2.3): `spawn(process.execPath, [...(app.isPackaged ? [] : [app.getAppPath()]), '--remote', host], { detached: true, stdio: 'ignore' }).unref()` — the dev `electron` binary needs the app path, the packaged one must not get it. Its window shows the **connecting screen** driven by `transport:state`: *Connecting… → Starting orc server… → Ready*, or `busy` (§6), `error` (ssh's stderr verbatim, with hints for the common cases: "Permission denied (publickey)" → add your key to the agent; "Host key verification failed" → ssh to the host once in a terminal) and **Retry**.
- Connected: sidebar header chip `ssh: devbox`, window title `orc — devbox`, **Open folder…** becomes the remote picker (§7.3).
- **Disconnected** (ssh exited): banner *"Disconnected — reconnecting…"*, exponential backoff 1 s → 30 s, **Reconnect now**. Reconnect spawns a new ssh/server; the previous server has exited (EOF or ping timeout), so **running turns were interrupted** and the chat reloads its history from `~/.claude` on the host. The renderer does not re-run `init()` (it would double-subscribe its five `api().on` listeners); `init()` only subscribes and calls `transport.state()`, and the data fetches (lists, settings, statuses, models) move into a `load()` that runs on every `ready` — the first one included, on the local transport too, so nothing is fetched twice — clearing `transcripts`, `status`, `models`, `account` and re-selecting `activeId`.
- `taken-over` is a terminal phase: no backoff reconnect (it would land on the busy screen and replace the banner). Banner *"Taken over by alice@devbox"* with **Take back** (`hello` with `takeover: true`).

### 7.3 Folder picking
`projects.add(path?)`. On a local target the desktop IPC layer shows the native dialog when `path` is absent and forwards the result (the three renderer callers — palette, composer strip, sidebar `+` — are unchanged). On a remote target the renderer opens a picker fed by `projects.browse(path) → { dirs, parent }` (server-side `readdir`, dotfiles hidden, starting at the host home dir) and calls `add(path)`. The renderer branches on `transport:state.kind`.

### 7.4 SSH launcher (`src/main/remote.ts`)
- Spawns the **system `ssh`**: `ssh -T -o BatchMode=yes -o StrictHostKeyChecking=accept-new -o ServerAliveInterval=15 -o ServerAliveCountMax=3 <host> 'exec ~/.orc/<version>/orc-server --stdio'` — an absolute path to the bundle (sshd still runs it through the user's login shell with `-c`, but nothing depends on the profile, PATH, or a Node on the host). Keys, agent, `ProxyJump`, bastions and `~/.ssh/config` all work with no code (`Include` directives in the config are honoured by ssh itself, though the host *picker* does not follow them). Phase 2 is key/agent-only: `BatchMode=yes` turns a password prompt into a clean error. A missing bundle in phase 2 surfaces as the ssh exit 127 → error screen *"orc-server is not installed on devbox"*.
- Phase 2 gets the bundle onto a test host with `scripts/dev-remote.sh <host>`: run the SEA build of §8 locally for the host's target, copy the platform `claude` beside it, `scp` both into `~/.orc/<version>/`. Dev-only; phase 3c replaces it with the automatic install.
- Phase 3b: drop `BatchMode`, set `StrictHostKeyChecking=ask`, `SSH_ASKPASS=<helper>` + `SSH_ASKPASS_REQUIRE=force`, and add `-o ControlMaster=auto -o ControlPath=<per-instance tmp socket> -o ControlPersist=60` so a reconnect within 60 s reuses the authenticated connection; the helper (shipped outside `app.asar`) connects to a per-instance Unix socket (`0600`, random path) and the connecting screen shows the prompt — password, passphrase, 2FA, and host-key confirmation. VS Code's approach. (`accept-new` in phase 2 still refuses a *changed* key.)
- Phase 3c remote command is a bootstrap, so install and launch happen in **one** ssh invocation (one askpass round): the bootstrap checks `~/.orc/<version>/orc-server`, runs the install route of §8 inline if it is missing (emitting `install` frames), then `exec`s the server by absolute path — no login shell, no PATH, no Node. sshd hands the command string to the user's login shell (possibly fish or tcsh) before `sh` sees it, so the bootstrap is shipped base64-encoded and started as `sh -c 'eval "$(printf %s <b64> | base64 --decode)"'` (`--decode`, not `-d`: older macOS `base64` only knows `-D`/`--decode`) — the outer **single** quotes make every login shell (sh, bash, zsh, fish, csh, tcsh) pass the text literally, so the `$(…)` substitution runs inside `sh`, not in the login shell (fish < 3.4 and csh have no `$(…)`); the base64 alphabet contains no `'`, `\` or `!`, stdin stays attached for the server, and `exec`/traps inside the script behave as written.
- Server lifetime = the ssh connection: closing the window ends ssh → stdin EOF → `closeAll()`, lock released. For that to hold on macOS, a remote instance quits on `window-all-closed` (today's darwin behaviour of staying in the Dock applies to the local instance only), and `before-quit` sends `{"shutdown": true}` and ends stdin. Re-attaching to a server that outlives its window (`--keep`) is a second transport (detached process + host-side Unix socket) and is **out of this plan**.
- Clients: macOS and Windows (electron-builder targets mac + nsis); Windows hosts are supported too (§15). Linux clients are untested.

## 8. `orc-server`

- `orc-server [--stdio] [--data-dir <dir>]`; `--stdio` is the only transport. A loopback WebSocket for browser clients could later sit behind the same `handlers.ts`.
- **Default data dir = the local app's `userData` on that OS** (`~/Library/Application Support/orc` on macOS, `$XDG_CONFIG_HOME/orc` or `~/.config/orc` on Linux), computed without Electron, with `ORC_DATA_DIR` overriding both sides the same way. This is what makes "open A locally, then connect to A from B as the same user" one target: same `projects.json`/`sessions.json`/`settings.json`, same `~/.claude` transcripts, and the same lock file — so a still-running local orc on A produces the take-over dialog rather than a second engine. A different ssh user is a different target (different home).
- **What Claude Code is here.** `@anthropic-ai/claude-agent-sdk` is a thin JS wrapper plus, via per-platform optional dependencies (`…-sdk-darwin-arm64`, `…-linux-x64`, …), one ~256 MB standalone `claude` executable — the complete agent, no Node inside. orc never uses a separately installed Claude Code; it points the wrapper at this binary (`pathToClaudeCodeExecutable`, as the packaged desktop app does today). A terminal Claude Code on the same machine is a different binary and version, but shares `~/.claude` (credentials, settings, transcripts), so its sessions and orc's coexist.
- **Host prerequisite: ssh only** (plus internet access for the one-time download). Everything else is installed and configured by the desktop app on first connect (phase 3c); in phase 2 the dev script of §7.4 pushes the same bundle so the transport is proven before the installer and CI exist.
- **Self-contained bundle** (phase 3c): `orc-server-<target>.tar.gz` ≈ 155 MB download, ≈ 380–400 MB on disk = `orc-server` (a Node **Single Executable Application**: the engine + SDK wrapper bundled to one CJS file and injected into a stock `node` binary) + that platform's `claude` binary as a **sibling file**. Runtime: the exact Node version Electron ships — Electron 44.9 → **Node 24.22.0** (`ELECTRON_RUN_AS_NODE=1 electron -p process.versions.node`), pinned as a full version in one place and bumped together with Electron — so the engine, reducer and SDK wrapper run on one runtime locally and remotely and the fake-SDK suite, which runs under Electron's Node, covers the remote path too. Build (`scripts/build-server.mjs`, runs on a macOS machine for any target): bundle `out/main/orc-server.js` and its chunks to a single CJS file with esbuild (added as a devDependency, together with `postject`; `--format=cjs` plus an `--inject` shim `export const __importMetaUrl = require('url').pathToFileURL(__filename).href` and `--define:import.meta.url=__importMetaUrl`, since `--define` takes no expressions — this covers the SDK wrapper's two `import.meta.url` uses, its only ESM-isms); fetch the official `node-v24.22.0-<target>.tar.gz` for each of the four targets **plus** the runner's own `darwin-<arch>` from nodejs.org, verify against `SHASUMS256.txt`, and keep only `bin/node` (cached); generate the blob **once**, with the downloaded darwin `bin/node` of the pinned version (never the PATH `node`) and `useCodeCache: false, useSnapshot: false` — without a snapshot or code cache the blob is platform-independent (script bytes plus metadata; all targets are little-endian 64-bit), so the same blob is injected into every target binary, which is what makes building the Linux targets on a macOS runner possible; `postject <target bin/node> NODE_SEA_BLOB sea.blob --sentinel-fuse NODE_SEA_FUSE_fce680ab2cc467b6e072b8b5df1996b2` (plus `--macho-segment-name NODE_SEA` for darwin); on macOS targets `codesign --remove-signature` before and an ad-hoc `codesign -s -` after (an unsigned arm64 Mach-O is killed at exec, which is why the build host is macOS; Linux targets need no signing). The flag is still `--experimental-sea-config` in Node 24 (stability 1.1). `cli.ts` switches on `require('node:sea').isSea()`: in a SEA it passes `pathToClaudeCodeExecutable: join(dirname(process.execPath), 'claude')`; under plain `node` in development it omits the option and the wrapper resolves the installed platform package itself. In a SEA `process.argv` is `[execPath, <invoked name>, ...args]`, so `argv.slice(2)` works in both modes. Targets and the `uname -sm` map: `Darwin arm64`→darwin-arm64, `Darwin x86_64`→darwin-x64, `Linux x86_64`→linux-x64, `Linux aarch64`→linux-arm64. The bootstrap refuses before downloading, with `unsupported-host`, when `/lib/ld-musl-*` exists (official Node has no musl build) or `getconf GNU_LIBC_VERSION` is below 2.28 (the floor for official Node ≥ 20 binaries; Ubuntu 18.04 / CentOS 7 would otherwise download 155 MB and die at `exec` with a loader error). Published as GitHub release assets at the app's version with SHA-256s in `bundles.json`; the bundle's `claude` is the version the SDK pins (CI can reuse the SDK's own `manifest.json` checksums), so engine and agent are always a tested pair, at the cost of a bundle refresh per orc release.
- **Install on first connect** (phase 3c, inside the bootstrap of §7.4): if `~/.orc/<version>/orc-server` is missing — the connecting screen shows *Installing orc server on devbox (150 MB download, one time)…* — the bootstrap — which embeds all four `bundles.json` URL/SHA-256 pairs, since the target is only known after its own `uname -sm` — stages into `~/.orc/.tmp.<version>.<pid>/`: `curl -fsSL <release url> -o bundle.tgz`, compare `$(sha256sum bundle.tgz | cut -d' ' -f1)` (or `shasum -a 256`) with the expected digest as strings (never `-c`, whose `OK` line would land on stdout), `tar xzf` into the staging dir (the tarball is flat: `orc-server` and `claude` at the top level), then `mv` it to `~/.orc/<version>/`. A partial install therefore never looks installed. Concurrency: POSIX `mv` moves a directory *into* an existing target (`mv -T` is GNU-only), so if another laptop finished first the loser's staging dir lands nested inside the winner's; the success test is `[ -x ~/.orc/<version>/orc-server ]`, followed by `rm -rf ~/.orc/<version>/.tmp.*`. The bootstrap sets `trap 'rm -rf "$staging"' EXIT` and `trap 'exit 1' HUP INT TERM PIPE` so a window closed mid-download does not leave 400 MB behind (the final `exec` replaces the shell, so the trap cannot delete a finished install). The host always downloads the bundle itself; there is no upload path. A host without `curl` or without internet access gets `{"error": "install-failed", "reason": "no-curl"|"download"}` and the error screen says so; such hosts are out of scope. Host needs only `sh`, `tar`, `gzip`, `sha256sum`/`shasum`, `base64`, `uname`, and `curl`. **Pruning** of other `~/.orc/<v>/` dirs is done by the server itself right after it takes the lock, never by the installer — otherwise a laptop on an older orc that currently holds the lock would lose its `claude` binary under a running server. The pruner keeps the two newest versions and any version a running `orc-server` is executing from (`pgrep -f ~/.orc/`; two data dirs on one host share `~/.orc`), and removes `.tmp.*` dirs older than a day.
- **Credentials: forwarded from the laptop** (phase 3b). Claude Code has a long-lived subscription token for headless use: `claude setup-token` (confirmed in the bundled CLI 2.1.302; it is a browser flow on the user's own machine) and the CLI honours `CLAUDE_CODE_OAUTH_TOKEN`, preferring it over a stored credential. The desktop runs `setup-token` once ("Sign in for remote hosts…"; stored with Electron `safeStorage` in a file under `userData`, with an `ORC_OAUTH_TOKEN` override for tests, since a raw keychain item prompts under the test runner), sends it in `hello.oauthToken` over ssh, and the server passes it **only in the SDK `env` option** (`query({ env: { ...process.env, CLAUDE_CODE_OAUTH_TOKEN } })` through the codec config — the SDK's `env` replaces the child environment; the server's own `process.env` stays clean so `ps`/`pgrep`/`auth status` helpers never inherit it) — never on the host's disk; it is a per-process secret with the lifetime of the server. Both sides redact it from logs. If no token is sent, the server falls back to the host's own `~/.claude` login; the `auth status --json` check runs only in that fallback case (with a token present the CLI reports `loggedIn: true` without validating it), with the instruction *"Sign in for remote hosts in orc, or run `ssh -t devbox <path>/claude auth login`"*. A revoked or expired token surfaces as the CLI's auth error on the first turn; the codec maps that error to a `transport:state` hint *"Sign in for remote hosts again"*. `setup-token` tokens last 365 days and default to the `user:inference` scope, so `initializationResult().account` may lack `email`/`subscriptionType` on a remote target — the account chip tolerates missing fields. (`CLAUDE_CODE_OAUTH_SCOPES="user:profile user:inference"` at `setup-token` time would restore them; worth a smoke test, not required for chats.)
- `files` listing, `bashEditDiff`, subagent transcripts: already server-side, unchanged.

## 9. Security

- No TCP listeners anywhere; authentication *is* SSH. The only sockets are the local askpass Unix socket (phase 3b). Local transport stays Electron IPC.
- The server runs with the host user's rights, like `claude`; `projects.browse` is a convenience over `readdir`, not a sandbox.
- `hello.client` is informational (shown in the take-over dialog), never used for authorization.
- The forwarded OAuth token is as sensitive as a password: it travels only inside the ssh session, lives only in the server process's environment (inherited by `claude`), is never written to the host's disk or logs, expires after 365 days, and is revocable from the user's Claude account — hence the "Sign in for remote hosts again" path in §8. Anyone with shell access as that user on the host could read it from the process environment for the session's duration — the same exposure as a terminal login there.
- The bundle download is pinned to a release URL at the app's version and verified on the host against a SHA-256 shipped inside the desktop app (`bundles.json`) after download and before unpacking (staging dir + `mv`, §8).

## 13. Deferred / cut

- `--keep` (server outliving its window): needs a re-attach transport; separate design.
- Login relay through the UI: replaced by token forwarding, with the instruction string as the fallback (§8).
- Server bundles *inside the desktop app*: replaced by release-hosted bundles the host downloads (§8); the DMG stays small.
- Multi-client attach: excluded by the exclusivity decision; the engine's `push()` fan-out would make it cheap later.
- Directory renames (`main`→`desktop`, `renderer`→`client`): no behaviour, several config edits.
- Linux clients (nothing in the code prevents it; not built or tested).

## 14. Risks

- **Building the server**: SEA is official but still flagged experimental in Node 24 (`--experimental-sea-config`, stability 1.1); the known constraints — CJS entry, `require()` of builtins only, `import.meta.url` shimmed at bundle time, blob generated by the pinned Node version, no code cache/snapshot (which is what lets one blob serve every target) — are all satisfied by the build steps in §8, and the SDK wrapper never resolves its platform package because the bundle always passes `pathToClaudeCodeExecutable`. (Verified during review: the wrapper bundles to a 1.6 MB CJS file with no `import.meta` left, injects, signs, and runs with `isSea: true`.) Residual risk is a Node point release changing the SEA format; the Node version is pinned to Electron's and the per-platform smoke test is the gate. Node is the only toolchain — a failing platform is fixed, not routed around. Hosts outside the targets, musl/Alpine, and glibc < 2.28 are unsupported and refused before any download.
- **Bundle size and updates**: ≈ 155 MB download / ≈ 380–400 MB on disk per host per orc version (stock Node 24 `bin/node` ≈ 125 MB raw / 39 MB gzipped — the nodejs.org tarball is ~55 MB because it carries npm, of which only `bin/node` is kept; `claude` ≈ 268 MB / 117 MB), downloaded by the host in about a minute. Hosts without internet access or `curl` are out of scope. Release assets must stay available for every version a shipped desktop app may ask for.
- **Token forwarding**: depends on `CLAUDE_CODE_OAUTH_TOKEN` and `setup-token` staying supported (both present in CLI 2.1.302 and documented in the SDK); if removed, the fallback is the host-side login instruction, which still works.
- **Take-over interrupts work** on the previous owner's side by design; the busy screen says who holds the lock so this is never a surprise.
- **Clock skew** is handled by `clockOffset`; durations in the transcript are server-computed already.
- **Shared home dirs** (NFS): take-over is refused across hosts; the user must stop the other instance there.
- **Hostname drift**: macOS hostnames change with the network (`Foo.local` vs `foo.lan`), so after a crash plus a network change a *local* lock can read as "controlled from another machine", and `holder.client` equality for auto take-over can miss. Not a correctness issue (nothing is taken over wrongly); if it bites, compare a persisted random machine id from the shell-local file instead of `os.hostname()` for the local kind.
- **Two users, one host, different data dirs**: not a conflict — the lock is per data dir and `~/.claude` is per Unix user.

## 15. Windows (added after the phases above)

- **Client.** Same code; `ssh` is Windows' built-in OpenSSH. Its OpenSSH has no connection multiplexing, so the `ControlMaster` options are skipped there (a password host asks once per connect). The askpass helper is a `.cmd` beside the helper script and the prompt socket is a named pipe (`\\.\pipe\orc-askpass-<pid>-…`); `DISPLAY` is set to a dummy value for OpenSSH builds older than 8.4, which need it before they use askpass. Window chrome: `titleBarOverlay` with the OS controls top-right, so the top bars get `padding-right` through `:root[data-platform="win32"]` (the preload tags the document with `process.platform`). Shortcuts are already Ctrl-or-⌘.
- **Lock.** `process.kill(pid, 'SIGTERM')` is a plain kill on Windows, so the holder watches `<dataDir>/takeover` (`fs.watchFile`, 300 ms) instead of a signal and leaves gracefully; the taker waits the same 5 s and then `taskkill /T /F` ends the tree. Start time comes from `Get-Process`'s `StartTime` (PowerShell, ~0.3 s, only on lock operations).
- **Host.** The first connect sends the Unix bootstrap; a Windows host answers with cmd's or PowerShell's *'sh' is not recognized* (or, with Git's bash as the login shell, the script's own `windows-shell` error on a MINGW `uname`), the client remembers the host as Windows in `shell.json` and retries with the Windows command: `cmd /c "powershell -NoProfile -NonInteractive -ExecutionPolicy Bypass -EncodedCommand <utf-16le base64 of bootstrap.ps1> && %USERPROFILE%\.orc\<v>\orc-server.exe --stdio"`. Both cmd and PowerShell login shells pass that through untouched; the chain is cmd's, so the server inherits ssh's stdio directly. `bootstrap.ps1` mirrors the sh one: `curl.exe` (Windows 10 1803+), `Get-FileHash`, `tar.exe` (bsdtar, reads tar.gz), staged into `%USERPROFILE%\.orc\.tmp.<v>.<pid>`, `Move-Item` into place, `finally` cleanup. The whole command is ~5 KB, under cmd's 8191-character line limit; each bootstrap only embeds its own platforms' bundle rows.
- **Server bundle.** `win32-x64` and `win32-arm64` targets: `node.exe` from the official zip, the same blob injected with postject (PE), no signing, `claude.exe` from `@anthropic-ai/claude-agent-sdk-win32-<arch>` beside it, still a `.tar.gz`. `cli.ts` looks for `claude.exe`, prunes with `Get-CimInstance Win32_Process` instead of `ps`, and the data dir is `%APPDATA%\orc` as for the local app. CI smoke-tests the Windows bundles on Windows runners.
- **Verified here:** the bundle builds and `orc-server.exe` is a valid PE32+; the sh/cmd detection and retry is covered by `transport.spec`. **Not verified on a real Windows machine:** Win32-OpenSSH launching a `.cmd` askpass, PowerShell 5.1 running `bootstrap.ps1`, and the lock's `watchFile` eviction — first things to check on Windows.
